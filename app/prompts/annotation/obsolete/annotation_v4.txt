GENERAL EXTRACTION RULES
1. Return exactly the ten required top-level keys and no extra keys.
2. "Persona" is the phrase after "As a" or "As an", without the article.
3. Use only facts stated explicitly in the user story. Do not invent actions, entities, attributes, or relations.
4. Every item in triggers, targets, and contains must be an array of exactly two strings.
5. Preserve tense, participles, or adverbs (e.g., "stored" → "stored"; "securely stored" → "stored").
6. Do not replace verbs with synonyms; use the exact verb from the text after normalization (e.g., if the text says "stay clean", use "stay", not "keep").
7. Preserve phrasal verbs exactly: "sign up", "log in", "log out", "walk through", "re‑watch".
8. Remove only articles (a, an, the) and possessive determiners (my, your, its) when they do not change the entity’s meaning. Do not remove other adjectives unless they are purely optional/descriptive.

GOAL ACTION EXTRACTION
1. GoalAction contains the canonical action labels requested by the user in the "I want to" clause.
2. Use the shortest meaningful base verb or phrasal‑verb label. Never include an object, article or context phrase in an action label.
3. Split independent coordinated goal actions:
   - "create named lists and add saved spots" → ["create", "add"]
   - "copy an itinerary and adjust dates" → ["copy", "adjust"]
   - "drag and drop stops" → ["drag", "drop"]
4. Extract verbs found only inside a descriptive relative clause or a prepositional phrase.
   - Example: "walk through a tutorial that demonstrates how to import a spot" → GoalAction is only ["walk through", "import", "create", "generate"].
   - Example: "manually add a spot by entering its name" → GoalAction is ["manually add", "entering"];
5. When the user explicitly asks the application to perform an action (e.g., "have the app generate"), include that action as a GoalAction.

GOAL ENTITY EXTRACTION
1. GoalEntity contains the direct noun phrases affected by a GoalAction.
2. Prefer the exact semantic object, not the whole clause:
   - "change the name of an existing list" → ["name"] (the action directly affects "name")
   - "filter the map to show spots" → ["map"]
   - "view the generated itinerary" → ["generated itinerary"]
3. Keep only essential adjectives that distinguish the intended object from other possible objects. Essential adjectives are those that are part of the entity’s identity, such as:
   - "saved spot", "saved spots" (distinguishes from unsaved)
   - "private notes"
   - "named lists"
   - "travel data"
   - "read‑only web link"
   - "generated itinerary"
   - "day‑by‑day itinerary"
   - "complete itinerary"
4. Remove nonessential articles and possessives:
   - "my email" → "email"
   - "an existing list" → "list" (if it is not the direct object; but if it is, we drop "existing" per rule 3)
5. Split explicit coordinated entities:
   - "spots and trips" → ["spots", "trips"]
   - "start date, end date, or total number of days" → ["start date", "end date", "total number of days"]
6. Expand explicit alternatives that share a head noun, and carry over any preceding modifiers:
   - "saved TikTok or Instagram video" → ["saved TikTok video", "saved Instagram video"]
   - "existing Google/Apple account" – treat as a single entity (do not split) because the slash indicates a combined/alternative type, not separate entities.
7. Do not include examples or enumerations given in parentheses as GoalEntities (e.g., "private notes (e.g., reservation numbers or tips)" → GoalEntity contains only "private notes"). Those examples may be used in "contains" if they are components of the parent entity.

BENEFIT ACTION AND BENEFIT ENTITY
1. BenefitAction contains canonical actions from the "so that" clause that represent **positive outcomes** the user wants to achieve.
2. BenefitEntity contains the direct objects of BenefitAction.
3. Split coordinated benefit actions and entities when explicit:
   - "stored and synced" → ["store", "sync"]
   - "understand distribution and plan routes" → ["understand", "plan"] with ["spatial distribution", "routes"]
4. Do not put contextual objects such as devices, maps, lists, locations, or timing phrases into BenefitEntity unless they are the direct object of a benefit action.

RELATIONSHIP RULES
1. triggers: create [Persona, GoalAction] for every GoalAction.
2. targets: create [Action, Entity] for every explicit action‑to‑direct‑object relation. Only grammatical direct objects count – do not include adjuncts (e.g., "as a daily route", "on a map", "at a glance").
3. For alternatives or coordinated entities, create a separate target pair for each explicit entity (e.g., ["sign up", "email"] and ["sign up", "Google/Apple account"] if both are separate direct objects).
4. contains: create [ParentEntity, ChildEntity] pairs only when one entity truly contains another as a PART, COMPONENT, VALUE, or SUB‑ELEMENT.
   Detect containment from these linguistic patterns:

   a. EXPLICIT INCLUSION ("including", "such as", "e.g.", "like"):
      "itinerary including maps, spot details" → ["itinerary", "maps"], ["itinerary", "spot details"]

   b. POSSESSIVE forms: "its name", "its location", "my trip's itinerary" – treat these as containment: ["spot", "name"], ["spot", "location"], ["trip", "itinerary"].

   c. PARTITIVE phrases ("X of Y" → Y contains X):
      "name of an existing list" → ["existing list", "name"]
      "list of saved spots" → ["list", "saved spots"] (if both entities are extracted, add this pair)

   d. EXPLICIT DATA HIERARCHY: "trip with start date, end date" → ["trip", "start date"], ["trip", "end date"].

5. STRICT RULES for contains:
   - Both elements MUST be nouns (entities) from the US text.
   - Ask: "Is [child] truly a part/component/value of [parent]?"
     YES → add to contains
     NO  → do not add
   - PURPOSE ("for offline use") → NOT contains
   - CONDITION ("without internet") → NOT contains
   - LOCATION ("on a map") → NOT contains
   - METHOD ("by entering") → NOT contains
   - TIME ("before visiting") → NOT contains
   - Do not add a relation when it is merely implied rather than stated.
