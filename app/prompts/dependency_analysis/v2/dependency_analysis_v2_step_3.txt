DEPENDENCY DEFINITION
A dependency exists when one story's activity is operation_type CREATE for an entity, and the other story's activity is operation_type READ, UPDATE, or DELETE for the same or matched entity (as reported in a Step 2 classified match).
The CREATE story is always the prerequisite. The READ / UPDATE / DELETE story is always the dependent.

DECISION RULES
1. Evaluate every match in classified_matches independently, in order, and produce exactly one entry in "dependencies" for each one - a story pair can have zero, one, or several matches, since each story can contribute more than one activity, and every one of them gets a verdict.
2. A match qualifies as a dependency (obd_dependency: true) when one activity's operation_type is CREATE and the other's is READ, UPDATE, or DELETE.
3. A match does NOT qualify (obd_dependency: false) when both are CREATE, both are non-CREATE (e.g. both READ, one READ and one DELETE, or one UPDATE and one READ/UPDATE), or either is NON_CRUD.
4. For a qualifying match, set prerequisite_id / prerequisite_activity from the CREATE activity's story (use story_a_id if it was activity_a, story_b_id if it was activity_b; prerequisite_activity is that same activity object, unchanged), dependent_id / dependent_activity from the READ/UPDATE/DELETE activity's story in the same way, and match_type from that same match.
5. For a non-qualifying match, set prerequisite_id / dependent_id to "", prerequisite_activity / dependent_activity to null, and match_type to "".
6. Do not merge separate matches into one entry, do not report the same match twice, and do not drop a match just because it doesn't qualify - it still gets its own entry with obd_dependency: false.
7. Never invent a prerequisite/dependent id, activity field, or match_type that did not appear in the Step 2 input.
8. Before answering, check your output against rules 1-7. Reason through this internally but do not write out your reasoning.
